## 0. The answer to "why 311 keep_active / 0 purge"

**It is the missing provenance marker, by deliberate Phase 3C design — not a dependency or lifecycle bug.** Every Job in this tenant has **`data_origin IS NULL`** (348 of 348). The Phase 3C cleanup dry-run only proposes `purge` for a Job that is *synthetic* (`data_origin IN ('seed_demo','test_fixture')`) **and** dependency-free. With every Job unmarked, the synthetic test is never satisfied, so the dry-run correctly returned **all keep_active, 0 purge**. Phase 3C intentionally left the existing rows NULL so the demo stayed visible. The cause is therefore **(a) missing `data_origin`** + **(b) the keep-demo policy** — not dependency checks (those work) and not lifecycle classification (those work; nothing here is stale/archivable).

Phase 3C.1 fixes this by **deterministically marking the demo Jobs**, curating a small representative demo set, and excluding demo from the default operating view (with an explicit Show Demo Data toggle).

Name-only artificiality is never used.

## 3. Seed hygiene findings

- Demo Jobs come from manual seed scripts (`seed-mission-control-demo.ts` is the bulk source; `seed-project-tracking-demo.ts`, `seed-client-command-center-demo.ts`, `seed-job-closeout-demo.ts`, `seed-sports-peer-qa*`). **None run on app startup** (verified: not referenced in `server.ts`/`app.ts`) — so running the app does **not** recreate purged Jobs.
- The targeted seeds are **idempotent** (DELETE-by-pattern + `ON CONFLICT (tenant_id, job_number)`), but a re-run **does recreate** their Jobs (by design).
- **Gap:** the seeds do **not** set `data_origin`. **Step 2 fix:** seeds must stamp `data_origin='seed_demo'` on every Job they create, and target only the demo tenant — so future seeds are self-labeling and never populate an operational tenant unmarked.

## 4. Curated demo policy (deterministic, Step 3)

Target **~20–40 representative Jobs**, not 332. The curated set is a **reproducible rule**, applied in the cleanup dry-run (no flag column needed):
- **Keep curated:** the 16 explicitly-marked scenario Jobs (they intentionally demonstrate project-tracking, client-command-center, closeout, and sports-QA flows) **plus** a deterministic, ordered sample (e.g. `ORDER BY id`) filling any missing required states — recently-completed, blocked, missing-details, unowned, workflow, production, **linked Shoot** (the 2 legacy-linked), and an **archived** example.
- **Archive (excess demo):** the remaining mass-generated filler that carries canonical child records worth keeping for the demo's depth.
- **Purge (disposable):** synthetic filler with no protected dependencies (the 4 zero-dependency Jobs, etc.).

## 5. Default-view truth (Step 4)

Once Jobs are marked `seed_demo`, the existing active scope (which excludes `data_origin IN ('seed_demo','test_fixture')`) hides them — correct for an operational tenant. A **`show_demo`** parameter (default off; on for the demo tenant) will include `seed_demo` so the curated set is visible. **Invariant retained:** the active summary counts and the active rows use the same inclusion rules (one predicate layer), so `show_demo` toggles both together — never one without the other.

## 6. Cleanup approval gate (Steps 5–6)

The extended dry-run (Commit 2/5) will report, per Job: current + proposed `data_origin`, proposed action (keep_operational | keep_curated_demo | archive_legitimate | archive_excess_demo | purge | duplicate_review | manual_review), reason, last activity, dependency counts + blockers, curated-keep flag, confidence, seed/fixture source, and whether a current seed would recreate it. **No hard deletion runs without explicit approval of the candidate batch.** The Demo Studio tenant is **conclusively disposable** (name "Demo Studio", 100% seed-created, zero real client data) — that evidence will accompany any proposed batch purge.
